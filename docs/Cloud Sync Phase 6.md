# Cloud Sync Phase 6

## Phase 6に必要な変更点

Phase 5の実装には、同期の基本経路と送信待ちの再送処理がある。Phase 6では、次の変更をこの順序で進める。

| 領域 | 現在の状態 | 必要な変更 |
| --- | --- | --- |
| 競合の保持 | APIは`409 Conflict`とサーバー版を返し、Workerは競合結果を返す。ただし、ローカル版とサーバー版を永続化していない。 | `sync_conflicts`などのローカル構造を追加し、ローカル操作、サーバー版、編集元の版番号、解決状態を保存する。競合した送信待ちは再送ループに入れず、解決操作まで保持する。 |
| 版の更新 | `baseVersion`による楽観的同時実行制御がある。古い版を自動的に上書きしない。 | 利用者が選択または統合した本文を、サーバー版を`baseVersion`とする新しい操作として保存する。「最後にサーバーが受理した更新を採用する」は、無条件の自動上書きではなく、競合解決後の暫定方針として定義する。 |
| 入力と保存量の上限 | Workerにはパス、タイトル、本文の上限があるが、APIの入力検証と同じ定数で管理されていない。 | サーバーとWorkerで上限を一致させ、超過時は`400`を返して保存・変更ログ・送信待ちを一切作成しないことをテストする。 |
| 履歴と復元 | サーバーの変更ログは残るが、履歴を表示・復元するAPIとUIがない。 | ノート単位の履歴取得を追加し、復元内容を新しい版として保存する。既存の変更ログは削除しない。 |
| 同期状態UI | サイドバーには認証状態だけを表示し、送信待ち、失敗、競合を表示していない。 | Workerの同期結果をNoteServiceと画面へ通知し、同期中、同期済み、再試行待ち、認証切れ、競合を表示する。競合画面ではローカル版とサーバー版を確認できるようにする。 |
| 失敗回復 | 送信待ちはローカルに保持されるが、オンライン復帰、画面復帰、定期同期、指数バックオフの契機が不足している。 | `online`、`visibilitychange`、起動時、保存後を同期契機にし、再試行間隔を管理する。認証切れでは再ログインまで送信を停止する。 |
| フォルダーインポート | ディレクトリを再帰的に読み込み、インポート内容をローカルへ保存する。深さ、件数、並列数、キャンセルを制御していない。 | 入力上限と処理上限を設け、既存のローカル変更や同期済み基準版と衝突した場合に、三者マージまたは双方保持を行う。 |
| 件数と描画性能 | ノート一覧と一部の読み込み処理は全件を対象にし、仮想化やページングを導入していない。リンク検索用のSQLiteインデックスは存在する。 | ノート一覧をページングまたは仮想リストにし、必要なSQLiteインデックスを追加する。長時間のWorker処理はチャンク化し、キャンセル要求を反映する。 |

実装の主な変更箇所は、`functions/api/sync/validation.ts`、`functions/api/sync/notes/[noteId].ts`、`functions/api/sync/schema.sql`、`public/sqlite-opfs-worker.js`、`src/types/sync.ts`、`src/services/note-service.ts`、同期状態を表示するコンポーネント、`src/storage/file-bridge.ts`である。まず制約と競合データの保存形式を確定し、その後にWorker、API、UI、インポート処理の順で実装する。
